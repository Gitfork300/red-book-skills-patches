## 4 / 24 / 32 定位路径的演变（最容易踩错的一段历史）

- **2026-09-27 前**：首选 `/you/mentions` 主动 `fetch` → 实测 **406** → 一度判「已失效」。
  **错在用主动 fetch** —— 通知页**自己加载时**会调它并返 200。
  正确姿势：`Network.enable` → 监听 `Network.responseReceived` → `getResponseBody`（铁律 32 的做法）。
- 失效期替代三条路：
  - 私信列表页 **`/chat`**（不是 `/im`，/im 导航 45s 超时），会话条目 `[data-conv-id]`
    （class `xhs-im-conv-item`），一次拿全部会话（实测 101 个）。
  - 评论：优先读 `_*_pub_progress.json` 里的 `note_url`（发布链自 2026-09-27 起落盘，含 xsec_token）。
  - 老笔记补 token：`search_feeds(标题)` → 按 `note_id` 匹配 → 取 `xsecToken`（`_scan_old_comments.py`）。
- **主页只渲染最近约 30 条**：当天发满 30+ 篇后，昨天及更早的笔记在主页上**完全取不到 token**
  → 「扫了 32 篇、0 未回复」的**假阴性**，这是覆盖缺口根因，必须靠上面两条补。
- **创作中心 `_capture_note_manager_notes()` 的 token 不可复用**：10 条共用一个账号级 token（前缀 `YBey`），
  配 `/explore/{id}` 报 `This Page Isn't Available`。
- mentions 字段：`item_info.id`=note_id、`item_info.xsec_token`、`item_info.content`=笔记正文、
  `comment_info.id`=comment_id、`comment_info.content`=评论正文、`user_info.nickname`、`time`(unix)。
  实测 6 轮翻页得 **120 条**去重映射（A/B/D 路的 `__INITIAL_STATE__`、Vue 树均 0 命中，不必再试）。
- 用途：拿到 note_id 后按**笔记正文**定制答复（报名类能给到对应活动的具体网址），
  不再依赖 `_locate_v5.py` 的离线关键词猜测（其 LOW 级候选不可采信）。

## 6 / 22 / 27 判据的三处历史误判

- 昵称：由 `comment/post` 响应体的 `data.comment.user_info.nickname` 实测确认 = **`AI展会叻`**。
  此前按 `叻叻财` 判「已回」→ **恒为假**，大量已回复的评论被反复列进「未回复」。
  （不是前缀、不是非空 —— 用户手动回的不带前缀。）
- 私信已回：会话列表 `summary` 显示的是**最后一条消息，不论谁发的**；历史欢迎语没带 `[A2]` 前缀
  → 用「summary 是否以 `[A2]` 开头」判定会把**早已回过的**全标成待回（实测 99 个会话里 **20 条误判**）。
- `get_feed_detail`：返回结构是 `{"detail": {"comments": {"list": [...]}}}`。
  读顶层 `det["comments"]` **恒为 None** → 每篇都报 `comments=0`，
  曾让「遍历 67 篇、0 未回复」这个假阴性看起来像真的。

## 13 / 34 / 35 回不回的判定（配额制）

- 铁律 13 默认「非提问不回」，用户原话：「可能这是和其他朋友间的聊天或者标记，我们无需打断」。
- 2026-09-27 新增例外：**评价类（eval）在配额不足时才回**。
  「评价类」= 针对我方笔记内容发表看法/判断/感慨且**未提问**（如「京东废了」「微软也在整合AI产品」），
  区别于「闲聊」的点在于**对象是我方内容**，不是用户之间对话。
- 配额从 80% 下调到 **50%**（用户 2026-09-29 原话「评论比例可以降低至50%，减少无效回答」）。
- 分母 `planned` = 当日自然日收到的评论总条数（按评论发生时间归属，含所有类别、不预先剔除）。
- 优先级严格按序取，够数即止：`question` 必回（不受配额限制）→ `correction` 必回 →
  `eval` 仅在不足 `ceil(planned*0.5)` 时补 → `chat` 永不回。
- 补 eval 时**按评论时间由新到旧**，补到 `need` 条即停，**不许超额刷互动**。
- `planned <= 2` → 至少回 1 条；`planned = 0` → 不回。
- 结构性不可达：chat 占比 >50% 时 `cap = planned - chat_n < target` → 目标降到 cap，
  汇报标注「50% 不可达，已达理论上限 cap/planned」。
- 分类函数 `classify()` 在脚本里**单一出处**，SKILL 只给口径；**判据存疑 → 归 `chat`**
  （chat 永不回，误归代价是少回一条；反过来会打断他人对话）。
- 跨自然日：`planned` 按评论时间归属，36h 窗口会跨到昨天 → **昨天的评论算昨天的分母**，
  收尾分别报"今日覆盖率"与"昨日覆盖率（若有补回）"。

## 26 / 28 / 31 / 33 / 36 通知页链路（就地回复）

- 26 的对法：通知页 `/notification` 默认停在「赞和收藏」tab，
  **必须先点「评论和@」**（innerText==='评论和@' 且 children.length===0），一次约 20 秒抓 100+ 条（实测 170 条）。
- 28 的反面教材：`_scan_notif_v2.py` 用 `/已回复|回复了/` 匹配整块 innerText 判「已回复」，
  而通知里的**动作文本「回复了你的评论」本身就含「回复了」** → 恒定命中 → 系统性漏回复（脚本已废弃）。
- 28 的再修正：**「有回复按钮」⇏ 未回复** —— 该按钮是常驻快捷入口，回复后依旧存在；
  真正判据 = 条目 innerText 含**我方回复正文片段**，或看 `comment/post` 响应体。
- 31 的事故与解法（2026-09-27 19:00 实测，**已解决**）：
  - 现象：`.submit` 非 disabled 且 `click()` 返回 `sent`，但评论下没有这条回复、也不报错。
  - 已排除：不是填错对象（`n_ta=0` 无残留隐藏输入框）、不是文案过长（85~100 字 < 150 字线）、
    **不是风控**（页面「风险词」检测 = ok）。
  - 根因 = **点击落空**：`element.click()` 对 Vue 发送按钮不产生真实事件（UI 清空输入框看着像成功，
    但**根本没发请求**，`Network` 里只有 `unread_count`）。
  - 正确姿势：先 `scrollIntoView({block:'center'})` **再**取 `getBoundingClientRect()` 算坐标
    （不滚就取坐标会落到视口外）→ 用 **CDP `Input.dispatchMouseEvent`**（mousePressed+mouseReleased）
    → 用 **`Input.insertText`** 键入（触发 Vue v-model），别直接改 value 派发事件。
  - 验收 = 网络出现 `api/sns/web/v1/comment/post` 且响应体含 `"toast":"你的回复已发布"`。
    脚本 `_fix_send.py`、`_post_resp.py`。
  - ⚠️ 监听判据**不能写成 `"/api/sns/" in url`**：`unread_count`、`you/mentions` 都含该串 → 恒定命中
    → 假阳性。必须写 `"comment/post" in url`。
- 33 的环境坑：新 Chrome 实例首次导航常被踢到 `/login`（「电脑设备登录超限」），
  **重试 2~4 次即可进入**（中间穿插导航 `/explore` 预热）；**千万别 `--restart`**（每次重启掉一次登录态）。
  脚本里必须清掉 `HTTP(S)_PROXY/ALL_PROXY`，否则 CDP 连 `127.0.0.1` 被本机代理劫持（502）
  → 误判 Chrome 已死 → 触发重启 → 又掉登录。
- 36 的事故：子评论在笔记详情页**默认折叠**，未展开查 `[A1]` → 0 命中 = **假阴性**，与「真没发出」表现一致。
  首轮 5 条发出后误判 2 条失败 → 补发 → 展开后发现 `[A1]` 出现 4 次 → 逐条删除才恢复。
  核验标准动作（`_expand_check.py`）：滚到 40%/70%/90% → 点所有 `/展开\d+条回复/` → 再滚 → 才数 `[A1]`。

## 15 / 16 / 17 / 18 / 19 / 20 / 25 / 30 环境与节流

- 17：用户原话「请在白天增加超时处理机制，白天不要瞎琢磨，要尽可能按时完成任务为主」；

- 18：由我自己的事故反推 —— 连续无间隔扫 54 篇 → 触发滑块验证码，之后所有导航卡死 180s 超时。
  恢复只能**在 Chrome 里人工拖一次滑块**。
- 19：用户原话「评论只需要关注 2 天以内发布的，不要追溯更久远的」；过滤维度是**笔记发布时间**，
  与铁律 7 的评论时间窗口不冲突（先用 19 定候选笔记，再在候选内处理）。
- 20：列表接口单次只出 100 条，新抓快照最旧只到 9/14 18:48，而评论最多的那篇正好在 100 条之外

- 25：自建 websocket 连 9333 会被本机 ALL_PROXY 劫持，**永久挂起且无任何报错**；
  `_send()` 只接位置参数 `_send(方法名, 参数字典)`，传 kwargs 会 TypeError。
  浏览器疑似已挂 → 先查 `http://127.0.0.1:9333/json/version`，挂了跑
  `chrome_launcher.py --port 9333 --restart`（skill 的 .venv python）。
- 30：本机 PowerShell 工具会被沙箱拦（`sandbox-center cmd decisionRecord missing`），Bash 的
  `ls` / `wmic` 也常失效 → 可靠写法是 Python `subprocess` 调 `powershell -Command`，
  **输出写文件后用 Read 读**。

## 21 回复长度

- 现象是 `send=sent_lv3`（按钮点到了）却**没有这条回复，且不报错**。
- 实测：461 字失败、189 字失败，**缩到 ~130 字一次成功**（同一条评论、同一脚本）。

## 29 风控「访问频繁」

- 表现：`Timed out waiting for search data` 与 websocket `no close frame received or sent`。
  **不是代码 bug，是速率限制**（2026-09-27 16:45 实测）。
- 立即**整批停手、不重试**（重试加重，铁律 18 同原则），静置约 2 小时；
  停手时**必须同时暂停周期性巡检自动化**，否则它会在静置期内自动触发、抵消等待。
- 恢复后首轮降速：`--gap` 拉到 8~16s，优先做只读扫描确认额度是否回来。

## 37 零废话（用户 2026-09-29 原话）

- 原话：「『感谢补充使用体验』这样的废话不要有。可以发表话题相关的看法。」
- 禁止单独成条的客套：「感谢分享 / 感谢反馈 / 感谢补充使用体验 / 谢谢关注 /
  笔记仅整理官方公开信息，仅供参考」。
- 回复侧**允许表达观点**（与发布侧「只陈述事实」不同），但不得编造数据、不得无来源断言。
- 写法：先接住对方的点（「orca 更新节奏确实快于 X」）→ 再补一条具体信息（版本节奏 / 平台支持 /
  实际差异 / 官方口径）。**不复读笔记原文**。
- 查不到可核对信息时：要么不回（代价 < 发一条废话），要么写「公开信息没查到 X，以官方公布为准」。
