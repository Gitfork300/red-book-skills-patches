# comment-reply-guard

> **体系：`comment`（评论体系）** —— 只管**评论与私信的读取 / 回复**，**不管笔记文案**。
> 与发布体系（`publish`）是两套独立体系：写作 / 配图 / 时效 / 间隔 / 预检规则**一律不适用于回复**。
> 已知交叉点：正文网址（发布禁 / 回复问报名时必须给）→ 见 `SYSTEMS.md` X1。

## 铁律速查（每条必须遵守）

1. **每条回复必须以标记开头**：`[A1]` 评论 / `[A2]` 私信 / `[A9]` 其他 / `[E1]` 异常，格式 = 标记 + **半角空格** + 正文。
2. `--comment-id` **必须带 `comment-` 前缀**（接口返回纯 id，DOM 属性带前缀，全等比较）。
3. 回复按钮是 **svg 图标（无"回复"文本）** → 按 `.reply.icon-container` 点击，**不能用 `respond-comment`**（大面积失败）。
4. 定位首选 **`/you/mentions` 接口**（CDP 抓响应体，**非页面内 fetch**），直取 `note_id + xsec_token + comment_id`。
5. 通知页 DOM **只能发现、不能回复**（拿不到 id）；回复路径 = mentions 定位 + detail 核对 + 点图标发送。
6. **已回复判据 = `subComments` 里存在我方昵称 `叻叻财` 的条目**（不是前缀、不是非空 —— 用户手动回的不带前缀）。
7. **增量回复**：先取「上次回复时间」（回复日志 mtime）做窗口，无法判断时兜底 **36 小时**。
8. 答复前**必须查证**：≥2 源、查不到如实说「以主办方公布为准」，**不许套模板**。
9. **报名类问题必须给具体报名网址**（`https://…`，当场核实可打开、一一对应），不能只说"官方渠道登记"。
10. **「到期提醒」类（"X 日踢我"）→ 登记 `COMMENT_REMINDERS.md` + 挂一次性自动化**，到期真去提醒；**禁止回「没法单独提醒」**。
11. 私信：**只处理 3 天内**（新朋友打招呼放宽 5 天）；**已回复忽略**（判据 = 消息区最后一条是我方 `.chat-item__bubble--me`）。
12. 回复节奏：每条 **≥35 秒**、单轮 ≤20 条；站外链接高风险，**控量 + 盯异常**。
13. **非提问不回复**（用户 2026-09-16 原话）：评论若**没有向我方提问**，一律不回 ——
    用户原话「可能这是和其他朋友间的聊天或者标记，我们无需打断」。
    - **该回**：明确向我方提问 / 咨询（怎么报名、有议程吗、是否收费、能否参加）、
      以及**针对我方内容提出质疑或纠错**（必须回应，承认并给准确口径）
    - **不回**：用户之间的闲聊与附和（"这是个趋势""已经去过了"）、**@ 的是别人而非本号昵称**、
      纯表情 / 纯 @ 标记 / 无实质诉求的自我抒发
    - 判据存疑时**归入「不回」**（与热度闸门同款保守口径）：打断他人对话的代价 > 少回一条
14. **历史标记合规复查**：本号只允许 `[A1]/[A2]/[A9]/[E1]`；出现过 `[X1]`、`[自动回复]`
    及误用 `[E1]` 的存量评论 → 列为待清理项，报用户拍板后处理（删除入口见 `refs/01-dom-and-scripts.md` 第九节）。
15. **Tab 与内存守护**（用户 2026-09-16 提醒「注意浏览器网页多开上限，避免内存不够用、死机」）：
    - 评论链路**必须自建独立 tab**（`PUT /json/new`）以隔离发布链，用完在 `finally` 里关闭 ——
      脚本崩溃会**留下残骸**，多轮累积会吃内存
    - **绝不碰 `creator.xiaohongshu.com` tab**（发布链的地盘，关掉 = 打断发布）
    - 每轮收尾跑 `_tab_guard.py`（只读）→ 有残留则 `--clean`（只清 `about:blank` 与 www 域）
    - 批量操作前先看一眼系统可用内存；吃紧时**降并发、分批跑**，不要一次开一串 tab
16. **单篇量大只回前 2 页**（用户 2026-09-16 原话：「如果同一个文章出现大量待回复，
    我只会回复前2页信息，避免长时间卡在同一个子任务」）：
    - 一篇笔记评论很多时，**只处理前 2 页**（≈ 页面已渲染的部分，**不额外翻页**去捞更深的）
    - 定位不到的（DOM 未渲染 / 滚不出来）→ **直接跳过，不重试死磕**；
      连续 2~3 次定位失败即放弃该条，转下一条或下个任务
    - 禁止为单条评论反复重试超过 ~3 轮；把时间留给覆盖面更广的待回
    - 收尾如实报出「跳过/未处理」清单与原因，交用户决定
17. **白天超时预算制**（用户 2026-09-16 原话「**请在白天增加超时处理机制，
    白天不要瞎琢磨，要尽可能按时完成任务为主**」）—— 与铁律 16 同一原则的两面：
    - **白天 = 保量优先**：先按时把量跑完；卡住的项**超时即弃、转下一条**，绝不深挖
    - **白天禁止**：重构脚本 / 跨源深挖 xsec / 复盘分析 / 为单条连换路径
      （今天「拍摄需要吗」删不掉连试 6 轮 4 个脚本 = 典型违规）
    - **预算**（用户 2026-09-16 18:17 **拍板确认**）：单项 ≤180s 且 ≤2 轮；单轮巡检 ≤30 分钟；
      白天窗口 08:00–22:00；同类 skip ≥3 停手
    - 执行器 `_daybudget.py`（工作区根，managed python 跑）：
      `status` 看时段 / `wrap --budget N --tag X -- <cmd>` **零改造套超时**（超时 kill，rc=124）/
      `skip` 手工登记；新脚本推荐 `from _daybudget import Budget` + `b.check()`
    - 弃项自动进 `_skip_<日期>.md`，**收尾必报 skip 清单**（含原因）交用户决定
    - 同类项累计 skip ≥3 → 判**系统性障碍**，白天停手转夜间
18. **读取/扫描也要节流，命中验证码立即熔断**（2026-09-16 23:4x 实测，由我自己的事故反推）：
    - 铁律 12 的节奏约束只管「回复」，**没管「读」** —— 但扫描同样吃风控额度。
      实测：连续无间隔扫 54 篇 → 触发**滑块验证码**，之后所有导航卡死 180s 超时
    - **批量扫描每篇之间 sleep 8~16s 随机**（`_scan_0916_night2.py --gap N` 可调）
    - 输出里出现 `captcha` / `Security Verification` / `Drag the arrow` 任一 →
      **立即 `break` 整批，不要重试**（重试只会加重风控），转人工：
      **在 Chrome 里拖一次滑块**才能恢复
    - 单篇 `subprocess.TimeoutExpired` **必须捕获**，只记 error 继续下一篇 ——
      未捕获会让整批崩掉、已扫结果前功尽弃（v1 就栽在这）
19. **评论巡检只管「2 天内发布的笔记」**（2026-09-16 用户原话：
    「**评论只需要关注 2 天以内发布的，不要追溯更久远的**」）：
    - 过滤维度是**笔记的发布时间**，不是评论时间 ——
      `_scan_0916_night2.py --since YYYY-MM-DD`（按 `time >= since` 过滤，字符串比较即可）
    - 更老的笔记**即使有未回评论也不追**：读取本身吃风控额度（见铁律 18），
      为几年前的笔记赔上验证码不划算
    - 与铁律 7 的「36 小时兜底窗口」**不冲突**：7 管的是**评论**产生时间，
      19 管的是**笔记**发布时间；先用 19 定候选笔记，再在候选内处理
    - 例外：用户点名要处理的单篇，手工指定 note_id 单独扫
20. **扫描范围 = 合并清单，不能只用新抓的**（2026-09-16 实测）：
    列表接口**单次只出 100 条**，新抓的快照最旧只到 9/14 18:48，
    而评论最多的「上海AI Agent活动9月17」（9/14 18:15 发）**正好落在 100 条之外**。
    → 必须合并历史快照去重（`_merge_notes_src.py`，本次 100+197 → **253 条**）后再扫。
21. **回复内容过长 → 平台静默丢弃**（2026-09-16 实测，坑很深）：
    现象是 `send=sent_lv3`（按钮点到了）却**没有这条回复**，且**不报错**。
    实测：461 字失败、189 字失败，**缩到 ~130 字一次成功**（同一条评论、同一脚本）。
    → 回复**控制在 150 字内**；长内容宁可压缩，不要拆条。
    且**发送后必须 API 复查**（DOM `verify` 同样不可靠，见「关键判据」第 4 条）。
22. **私信「已回」不能看 summary 前缀**（2026-09-16 实测）：
    会话列表的 `summary` 显示的是**最后一条消息，不论谁发的**。
    历史欢迎语没带 `[A2]` 前缀 → 用「summary 是否以 `[A2]` 开头」判定会把
    **我方早已回过的**全标成待回（实测 99 个会话里 **20 条误判**，逐个进会话查全是 `ME`）。
    → **必须进会话看最后一条 `.chat-item` 有没有 `.chat-item__bubble--me`**
    （`_dm_read_ctx.py`，只读）。列表页只能用来**发现**，不能用来**判定**。
23. **个人主页抓笔记 DOM 已改版**（2026-09-17 实测，旧脚本抓 0 条）：`a[href*="/explore/"]`
    是隐藏链接且不带 token，真 token 在 `a.cover` 的 href；`section.note-item` 带 `data-note-id`；
    要滚 `#userPostedFeeds` 而非 window。见 `refs/05-profile-dom.md`。

## 关键判据与坑（要点）

**主页登录态 ≠ 创作者中心**：读/回评论要 `www.xiaohongshu.com` 主页登录态；只验 `check-login` 会误判"已登录"。

**地域 × 时间差异化话术**：回复前先定城市（长三角 / 珠三角 / **中国香港** / **中国澳门**）与开始日，话术随分类变。
- 港澳**必须加**「前往需持有效港澳通行证及签注」，且不得表述为国家。
- 已办完的活动**如实说已结束**，不再引导报名。

**报名网址来源优先级**：官方报名系统直达页 → 承办方官网活动页 → 主办方公告页 → 官方咨询渠道。
素材文件通常**无 URL**（全量仅 1 个含 URL）→ 必须回捞官方页补全，核实后落盘 `xhs_publish/registration_links.md`。

**私信入口**：`/chat`（非 `/im`）；会话 ID = `data-conv-id`，直连 `/chat/<conv-id>`；新朋友打招呼同样带 `[A2]`。

## 标准工作流（可复制）

```
1. 拿 (note_id, xsec_token, comment_id)：/you/mentions 接口（CDP 抓响应体，滚动合并去重）
2. 逐篇 get-feed-detail 核对（不是 164 篇全扫）
3. 判「是否已回复」：subComments 里有没有昵称 叻叻财 的条目
4. 回复：--comment-id 带 comment- 前缀 / 或按 .reply.icon-container 点击发送
5. 回读验证：重新 get-feed-detail 确认 subComments 出现我方回复
```
