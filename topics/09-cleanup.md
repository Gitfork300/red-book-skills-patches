## 日终落盘清单（2026-10-13 定）

1. **核进度**：以权威 `_NNNN_pub_progress.json` 为准，逐条看 `status`；
   `__chain__ circuit_break` 是熔断标记，**不计入篇数**（10-13 曾 39 条记录 = 38 篇 + 1 标记）。
2. **清进程/端口**：无 python 后台、无 chrome 残留、无 <PORT_PUBLISH>/<PORT_COMMENT> 监听、watchdog 已停。
3. **清自动化**：当日创建的**一次性接力全删**；长期 recurring（如每日天气 08:00）保留。
4. **归档锁**：陈旧 `.lock` / `.hb` **外移**到 `xhs_publish/_archived/locks_YYYYMMDD/`（只归位不删）；
   当日 `.hb` 保留到次日作为证据。
5. **改文档**：`_publish_status_NNNN.md` 的「更新时间」改为最终落盘时间，
   并检查**阻塞项段落是否与当晚实际一致**（10-13 曾出现傍晚写的阻塞描述与夜间已解决的事实矛盾）。
6. **收口必须有兜底**：一次性收口档**可能到点不触发**（10-15 的 21:30 档未执行，B-052），
   当日靠主进程 22:30 手工补做。故：① **一次性自动化不得作为当日唯一收口手段**，
   须另有主进程日界后巡检或独立 recurring 兜底；② 收口动作（外移锁 / 删间隔开关 / 改台账 / 写交接卡）
   必须**幂等**，人工补做时不覆盖已有成果。

## 收尾触发词（2026-10-15 定，已固化进 skill）

用户说「**收尾**」「**落盘**」「日终收口」→ **立即执行**，不等补充指令。
权威流程在 skill `daily-closeout-guard/SKILL.md`（shared 体系，priority 60）。

- **触发即回执**：第一句固定回「收到关键词「<原词>」，正在执行：日终收口七步（标准 ≤30 分钟 / 加急 ≤5 分钟），
  目标 YYYY-MM-DD 收口 —— 核进度/停进程移锁/清自动化/外移锁/改状态与交接卡/写记忆/已知问题复盘」，
  让对方一眼确认**识别的词、要做的流程、预算与模式**；可当场纠偏，未纠偏就按回执跑完。回执后即开工，不计入预算。

- **标准 ≤30 分钟**做全六步（核进度 / 停进程移锁 / 清一次性自动化 / 外移锁 / 改状态+交接卡 / 写记忆）；
  **加急 ≤5 分钟**只做 1·2·3·5 步，第 4·6 步转次日。
- 卡住 >5 分钟（加急 >90 秒）→ 跳过 + 登记 `_BUGS.md` 或 `_NEXT_NNNN.md`，**不现场深挖**。
- 收尾**不新增发布**（漏发走 publish-loop-guard）、**不删数据**（只外移）。
- 回报三件事：实际篇数 / 已停进程与已删自动化 / 遗留项编号。

### 第 7 步 · 已知问题复盘与登记（2026-10-15 补）

> 教训：事故**只记不闭环**等于没记；收尾是唯一固定盘点窗口，必须占用。

1. **盘点**：`python daily-closeout-guard/helpers/bug_ledger.py --root <工作区>`（同编号多段会聚合，
   任一段「已修/已闭环」即算闭环；退出码 2 = 台账缺失）。2026-10-15 首次盘点：17 条 / **未闭环 13**。
2. **修**：只挑能顺手修的，**上限 2 项**、每题 ≤2 分钟；**修完必须复跑对应校验脚本**
   （`check_patch_versions.py` / `check_doc_layers.py`），绿了才回写「已修」，否则保持「未修」。
   **加急模式跳过本步**。
3. **登记**：新发现问题按 `B-0NN` 格式写 `_BUGS.md`（现象/影响/修复方向，不现场挖根因），
   同步进 `_NEXT_NNNN.md` 与当日 memory 日志。
4. **闭环回写**：本轮修掉的在标题加「已修」并写「修复于 YYYY-MM-DD」，**不删条目**（保留事故史）。

## 停链与守护（2026-10-15 定）

1. **停链与移锁成对做**：停 `_chain_*` 进程后**必须同时移走其 `.lock`**，
   否则 watchdog 的 `chain_alive()` 会因 `.hb`/`.log` 尚新（阈值 45/50 分钟）而判「活」，
   **最长 45 分钟不重拉**（B-050；实测移走 `.lock` 后 20 秒内即重拉）。
2. **长驻守护不用 Bash `run_in_background`**（B-051）：该方式绑 agent turn 生命周期（实测仅活 2m21s），
   且其沙箱禁写 `publish-interval-guard/state/`；须用
   `DETACHED_PROCESS｜CREATE_NEW_PROCESS_GROUP` 起、并给启动命令开沙箱豁免。
3. **收口档停进程前先核对自动化元数据是否已被改档**；与用户在线操作并发时主动让位；
   停进程规则收窄到「当日 `_chain_*` / `_watchdog_*`」，且**只执行一次**（10-15 曾因宽匹配误杀重拉）。

## 收口即停 · 次日等指令（2026-10-20 用户口径）

> 用户原话：「收尾后就停止了，不算空转。等我发起新一天的任务命令继续开始。」

1. **收口即停**：当日配额发完 / 触发收尾 → 链直接停，**停在禁发窗口之前不算空转**，
   不因此判缺陷、也不必为「填满到 23:45」而加发。
2. **链的截止参数（如 `_watchdog_10NN.py 23:50`）只是保险线**，不是目标收口时间；
   实际收口以「发完 + 收尾七步完成」为准。2026-10-20 起默认值随禁发窗口改为 23:45，
   但**是否传都行**，不影响行为。
3. 🔴 **不得自动开次日**：日终落盘后**不预建次日仓、不起次日链、不挂次日开工自动化**。
   只有用户显式发出「开始新一天的任务」（或等价指令）才开工（铁律 21）。
4. 现存长期自动化（评论巡检 14:30/20:30、天气监控 08:00）属**既定周期性任务**，不受本条约束；
   当日一次性自动化（如 `10-NN 发布链巡检`）按收尾七步在当日删除。
