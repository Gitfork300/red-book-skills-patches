## A. 开工与任务树

18. **开工任务树**：1根+9子，建仓完开`[巡检]`，根收口→`start-daily-task`§6
21. **开工须等指令**：「开始新一天的任务」=授权跑全流程；**收口即停不算空转**，无此指令**不得自动开次日**（原文在 `../MEMORY.md`，本节给展开）

展开：
- 子任务由建仓、当天有实际内容的各组（A/B/C/E/F/G/H/Y/W/Z）、巡检、收尾组成；
  不为无配额分组建空任务。根任务负责收口断言 `published == jobs`。
- 分组只按 `topics/14-group-rules.md` 的现行组名建立；任务状态、排名、稿件和发布结果保存在业务工作区，
  不写入 Skill。`publish_log.json` 只供间隔守卫使用，不作为进度或分组台账。
- 建仓完成的标志是 `_BUILD_PRECHECK_*.md` 全部门禁通过（当前 4 道：时效、轮换、官方图、分组地域）。
- **建仓≠开工**。建仓只备料，不等到用户说出「开始新一天的任务」不得进入发布循环。

### A-1. 每日份数：排名翻倍 + 源闸门（Skill 规范见 `topics/14-group-rules.md`）

> 原话①：「每天计算一次文章观看和互动排名，当天可临时翻倍排名第 2 组的文章份数。」
> 原话②（澄清）：「**观看中位 互动 是两个排名，也就是有 2 组可以翻倍。同等排名也只选其中一个。**」
> 原话③（2026-11-06）：「**没有源的活动考虑删掉？等有源的时候也会检索到。请把缺口留给有源的符合要求的活动。**」

**开工第一步**（在建仓之前）：

```bash
cd xhs_publish
# ① 拉 D-1 日复盘数据（行数够才稳，--pages 16）
.venv python _fetch_review.py <D-1> --pages 16
# ② 排 D 日的两榜 → 写 _RANK_<MMDD>.json / .md
.venv python _daily_rank.py --date <MMDD> --out-json _RANK_<MMDD>.json --out-md _RANK_<MMDD>.md
# ③ 🔴 数源 → 源闸门（v1.3 必做；无源组配额归零，份数让给有源组）
.venv python _quota_source_gate.py --date <MMDD> --sources "A=3,B=3,C=2,E=0,F=0,G=2,H=2,Y=3"
#    --dry-run 只看不写；也可 --sources-file _SOURCE_AVAIL_<MMDD>.json
# ④ 生成队列（自动读闸门后的 final_quota，份数不再手写）
.venv python _gen_jobs_daily.py --date <MMDD>
# ⑤（可选）离线验证名额逻辑：合成用例覆盖撞车 / 顺延 / 人工覆盖
.venv python _test_rank_slots.py
```

**口径要点**（细节看 `_RANK_RULE.md`）：

| 项 | 规定 |
|---|---|
| 排名 | **两个独立榜**：观看榜（观看中位降序）、互动榜（互动数降序）。**不加权、不合并**，rank-sum 仅作展示 |
| 时序 | 用 **D-1 日发布**的稿件排 **D 日**的榜（当日数据排当日榜=鸡生蛋） |
| 翻倍名额 | **固定 2 个**：两榜**各**取第 2 名 → 当天最多 **2 组**翻倍 |
| 「第2名」定义 | 该榜降序后**第 2 个位置**；同值按组字母升序破平（保证可复算） |
| **撞车处理** | 两榜第 2 名**指向同一组** → **只选其中一个**翻倍，**另一名额作废**（**不叠成 ×4**），须显式记录 |
| 顺延 | 某榜第 2 名落 **Y**（不可翻倍）→ **在该榜内**顺延到下一可翻倍组，须记录原因 |
| 不翻倍 | **Y**（实验批次固定 5 篇，破坏可比性）、**W/Z**（不占固定配额） |
| 人工覆盖 | `--force-boost <组>[,<组>]`；覆盖 Y 或**超过 2 个** → 非 0 退出 |
| 总量 | 翻倍后 ≤ **28 篇**（22 基线 + 两个名额各 +3）；超限报用户 |
| 产能 | 14.5 min/篇（间隔均值10+执行4.5）；超**9h** 窗口 → **起链时刻前移**，不得再压缩 6–14min 铁律间隔、不得跳过 verify |
| 基线 | `_GROUP_QUOTA.md` **不改**，翻倍是当天临时值，次日自动回落 |
| 读字段 | `_RANK_<MMDD>.json` 的 `boost_groups` 是**复数数组**（`boost_group` 为首个，兼容旧读取方） |
| **🔴 源闸门** | `q' = min(翻倍后配额, 可用源数)`；无源组归零；让位 **A→B→C→G→H**（单组≤基线×2，Y/W/Z 不接）；让不出去的**下调总量，不转 Z 不挂账**（§5b） |
| **可用源四条件** | ① 时效在窗（会展开幕∈[D,D+7]）② 地域合规（**仅 E/F 受限**）③ 未判重 ④ **E/F 须有可下载官方图**（取不到即计 0）。**同源不可拆两篇** |
| 例外性质 | 突破 `_QUOTA_RULE.md` 20 篇锁定线，属用户**显式授权例外**（§五） |

**顺序不可颠倒**：排名 → **数源闸门** → 读 final_quota → 建仓按此写稿 → 生成队列 → 起链。
闸门若排在 `_gen_jobs_daily.py` 之后**不生效**（jobs 已按旧 final_quota 展开）。
`_gen_jobs_daily.py` **只认 `_RANK_<MMDD>.json`**，不接受手工数字（防"口头改篇数"绕过规则）。

**🔴 无源 ≠ 缺口**：检索不到合规活动 / 官方图取不到 / 已判重，都是「没有稿」，
当日该组配额归零即可，**不入 Z、不报缺口、不申请下调配额**。Z 只收「有稿未发」（铁律 11f-1、B-129）。

27. **收口硬停**：`--stop-after`不够→链内复判+stopper撤pending→`06`

展开（事故依据，都登记在 `xhs_publish/_BUGS.md`）：
- **B-048**：用 Bash 直接起发布链 → 抢不到/写不进锁文件，导致 B-048 整篇漏发。此后**链一律经 watchdog 起**。
- **B-056**：遇到 `chrome-error` 或登录态掉落，不要重试硬刚，返回码 5 停档；同一篇连续失败 2 次移到队尾。
- **B-057**：Chrome tab 数超过 10 会明显变慢并诱发后续失败，收口必须跑一次 tab 守卫清最早 8 个。**2026-10-25 升级**：用户铁律「任何阶段页签 ≤10」= <PORT_COMMENT>+<PORT_PUBLISH> 全局合计；合计 ≥10 回收至 ≤9（<PORT_PUBLISH> 留最新 3/<PORT_COMMENT> 留最新 1，login 不碰，每实例至少留 1 页）；10-25 晚实测 y1025_02 两连败（22:38 env 类 / 22:51 publish_error）与 tab 守卫无因果（首败 22:16:50 早于改动且与 watchdog 22:16:37 轮换 <PORT_PUBLISH> 重合）。
- **收口七步顺序不能省**：先逐条核 progress（篇数信 progress，**不信 publish_log**）→ 清进程/端口/看门狗 → 删一次性自动化 → 写 status 终版 + REVIEW/NEXT。
- **`--stop-after` 不可靠**：链内要自己再判一次，并让 stopper 撤掉 pending，否则会出现"计数到了但还在发"。

## E. 工程铁律与实例保活

25. **工程铁律**：数值/时间参数用`_val()`；判链死三重确认，进程死活看锁pid+心跳→`06`
26. **实例保活≤3h**：<PORT_PUBLISH>/<PORT_COMMENT>到点即重建不续命

展开：
- **所有数值/时间参数必须走 `_val()` 取值**，禁止在脚本里硬编码字面量（历史上多次因硬编码导致口径与规则脱节）。
- **判"链死了"要三重确认**再动手；判断进程是否真的活着，看**锁文件的 pid + 心跳**，不要只看进程名。
- Chrome 实例（端口 <PORT_PUBLISH> / <PORT_COMMENT>）保活上限 3 小时，到点就重建，**不要续命**（续命后的实例是失败高发源）。
- **B-095（写文件方式）**：`bash -c` 内联 Python 时，字符串里的**反引号会被 bash 当命令替换执行**，
  结果为空 → 文件被**静默写坏且 exit 0**。写含反引号或长中文的文本**一律用 Write / Edit 工具**；
  确需脚本就先 Write 成 `.py` 再跑。写完后 `grep` 关键反引号词确认存在，**不以退出码为准**。

### C-3. 🔴 进程判活口径（2026-10-28 取证，推翻 B-111 原定性）

**同名进程成对 ≠ 并发。** 本环境起 python 时会产生一个**父子同命令行的包装层**，
创建时间差 ≤ 1 秒，连临时脚本自己也是两层。因此「看到 2 个 publish_one」是常态。

| 判据 | 含义 | 处置 |
|---|---|---|
| 父子创建时间差 **≤ 1.5 s** | 包装层（1 真 + 1 壳） | **不算并发**，不要杀 |
| 父子创建时间差 **≥ 60 s** | 真二次启动（旧树未回收 + 被重拉） | **真并发**，立即停链 |

取证工具：`xhs_publish/_1028_proc_snapshot.py 1028`（输出 PID/PPID/创建时间/命令行 + 自动成对检测）。

**杀链 / 起链三条硬口径**：

1. **杀链必须连 watchdog 一起杀**（`taskkill /T /F` 整树）。
   只杀 chain/loop 会把 watchdog 留在那，它会在几秒内**自愈重拉链** ——
   表面看是「链又活了」，实际是你刚杀的那条被它复活。
2. **起链前先确认无存活 watchdog**，不只是无 chain。
   否则会出现两个 watchdog 各自判活（B-050 家族：两套口径）。
3. **Git Bash 下 taskkill 必须先 `export MSYS_NO_PATHCONV=1`**，
   否则 `/T` 被路径转换吞成 `T:/` → 报 `Invalid argument/option - 'T:/'`，**一个都杀不掉**。

```bash
export MSYS_NO_PATHCONV=1
taskkill /T /F /PID <pid>     # 整树，父死子也死
```

**外/内层 pid 与锁的一致口径（B-113）**：
链经 `Popen` 起的是**外层**，真正干活并写入 `_chain_<D>.lock` 的是**内层**。
只看外层会在「外层被杀 / 被会话回收、内层仍活」时误判链死 → 连拉被锁挡回 →
耗尽 relaunch 预算 → **watchdog 永久放弃**（B-114）。
判活口径 = **外层与内层任一存活即判活**。

**另两条衍生产门口径**：

4. **杀任何一层都必须带 `/T`**。不带 `/T` 杀链会让其下的 **loop / publish_one 变孤儿**，
   watchdog 重拉后会出现**两个 loop 抢同一篇**。杀完必须快照确认只剩 watchdog，
   再等它重拉；孤儿要单独 `/T /F` 清掉。
5. **起链脚本逐日由 `_make_chain_scripts.py --from <前一天>` 复制**，
   不在 runtime 里。修过 watchdog/chain 的当天，
   **次日必须用修好的那天做源**（10-29 用 `--from 1028`），否则修复丢失。

**心跳判活（B-115，2026-10-28 落地）**：
6. **watchdog 判活必须以「心跳文件」优先于「pid 存活」**。链（chain / loop /
   `publish_one` 守护线程）持续触碰 `_chain_<D>_hb_p1.txt`；任何链进程存活但卡死
   （如 loop 卡在 `reserve`/`publish` 子进程）都会让心跳陈旧 → 判死 → 杀树重拉。
   旧逻辑只看 pid 导致 04:23→08:29 静默停摆 4.75h。心跳文件**必须用 `open(a).close()`
   创建后再 `utime`**（`os.utime` 不存在文件会抛错被吞，心跳永远建不出）；
   `HB_TIMEOUT` 收到 20min（因有守护线程持续心跳，单篇最长 3400s 的发布不会误判）。
   重拉前必须先 `taskkill /T /F` 杀旧树并删锁，否则旧进程持锁、新链 `_acquire_lock`
   失败直接退出，重拉无效。
