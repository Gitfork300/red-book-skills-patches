## 三、执行器 `xhs_publish/_deadline_guard.py`

```bash
python _deadline_guard.py plan --total 24 --topic 12              # 反推最晚起跑
python _deadline_guard.py plan --total 24 --topic 12 --start 02:20
python _deadline_guard.py plan --total 24 --topic 12 --stop-at 06:00 --topic-from 02:00
python _deadline_guard.py check --date 1030                       # 此刻是否该熔断（rc=3 是）
python _deadline_guard.py cut   --date 1030                       # 砍半演练（dry-run）
python _deadline_guard.py cut   --date 1030 --apply               # 落盘 + 追加 Z 台账
python _deadline_guard.py status                                  # 规则表 + 典型反推
```

- `plan` 无 `--start` 时反推**最晚起跑**；`--start` 给出则评估该起跑是否达标（rc=3 不达标）。
- 起跑 ≥22:00 视作**前一日**；跨日时刻标 `-1d`。
- `cut` 规则：对每个仍有未发的组，按 key 排序后**保留前 ceil(n/2) 篇**，其余转 Z。
- `cut --apply` 写 `_DEADLINE_CUT_<MMDD>.json`，并把转 Z 条目追加进 `_Z_QUEUE.md`。

## 五、专题解禁的由来（2026-10-31 已裁定，**本节留档**）

解禁前：06:00–08:00 只有 120min ÷ 14.5min = **最多 8 篇专题**，而专题基线 9 篇（A3+B3+C3）、
翻倍后 12 篇 → **每天必然撞 08:00 熔断，专题被砍到 4–6 篇**。实测对比：

| 方案 | 起跑 | 非专题收口 | 专题收口 | 结果 |
|---|---|---|---|---|
| A 解禁前（专题须 ≥06:00） | 02:20 | 05:04 ✅ | 08:44 | ❌ 每天必熔断 |
| **B 解禁后（实际采用）** | 00:22 | 03:06 | 06:00 | ✅ 24 篇全链 06:00 收口 |
| C 解禁后 + 28 篇 | 前日 23:01 | 02:59 | 05:53 | ✅ 06:00 收口 |

用户最终裁定走 B —— 即**直接取消专题时间限制**，而不是把解禁时刻挪到 02:00。
