## 历史配额口径（2026-09-30，已由 2026-11-06 源闸门更新）

以下保留历史原因，不作为当前排期规则；现行无源配额处置见 `03-publish-rhythm.md` 的源闸门 v1.3。

- 原话：「**如果总篇数预计超过 20 篇，不能触发配额转移，空就行了**」。
- 含义：某组因时效过期 / 热度停更 / 预检挂掉而缺出的名额，**不许补给别的组扩容**，
  **空缺就空缺** —— 这是继上面「单篇无长尾」之后第二条收益边界：堆量不产生热度。
- ≤20 篇时也不自动补位，确需补位要显式报备源组/去向/理由并经用户点头。
- **根因**：`_REVIEW_RULE.md` v1.0 续停表原本写「停更该专题，配额转给其他选题」，照它执行就违规。
  已订正为「名额作废」，并加硬约束第 6 条；冲突时以 `_QUOTA_RULE.md` 为准。
- 建仓第一步 = 算当日各组计划篇数之和 N；N>20 立即锁定，任何组不加篇幅。

## ⚠️ 新专题（未发过稿）走冷启动，不适用 7/15 天窗（`_REVIEW_RULE.md` v1.2，2026-10-02 用户裁决）

- 用户口径：「某专题若满足热点 且 符合展会结束 T+2 → 继续发；不符合则停止」。
- **时效**：可发上界 = **活动结束日 + 2 天**。新专题**不得**因「未进 7/15 天窗」被提前判死。
- **热点**：新专题无历史 H → 不可判（禁止猜测）→ 走探针：**首发 ≥3 篇**（计入当日 N，禁事后追加）
  → **T+24h 取真数** → **H≥1.0 继续 / H<1.0 停止**。二分线 = `WARM=1.0`，与 `_review.py` 常量一致。
- 这条解决的是「新专题永远没有历史数据」的死锁 —— 没有它，任何新活动都无法开局。

## ⚠️ 预检不可事后重跑（2026-10-02 实测，假 FAIL 会误判成事故）

- `batch_preflight.py` 的 **[1] 查重项**拿稿件跟**发布台账**比对；稿件一旦发布就写进台账
  → **重跑必然报「与你自己完全相同」FAIL**，比对对象的时间戳正是它自己的发布时间。
- 实测：14:05 对已发的 can1002_01–04 与 d1002_01 重跑，全部 dup FAIL / rc=1，
  一度差点误判为"4 篇未过查重就发出去了"的事故。用 D 组做对照验证才排除。
- **结论：发布前的 rc=0 才是有效凭据。已发布稿件不要用预检复核**——
  要事后验质量，另用 check_wording / 字数统计等单项脚本，别跑 batch_preflight。

## 长发布链跑完必须清 tab（2026-10-02 实测）

- `_chain_live.py` 每发一篇开新 tab 不关：22 篇跑完累积 **51 个 page tab**。
- 清理法：按 URL 分组，每组只留**最后一个**（链最新在用的），其余 `http://127.0.0.1:<port>/json/close/<id>` 关掉。
  本次 51 → 5（notification / note-manager / publish / statistics / newtab）。
- 不清会让 Chrome 越跑越慢，影响后续巡检与次日发布。
