# publish-interval-guard / refs — 修改记录

- v1.6.1 (2026-11-06) 台账损坏时显式阻断，尊重自定义锁路径；状态迁移不覆盖既有台账，
  并统一现行 6–14 分钟口径和命令帮助。
- v1.5.0 (2026-10-22) **间隔 11–22min → 8–18min**：`DEFAULT_MIN` 660→**480**、`DEFAULT_MAX` 1320→**1080**；
  配套把发布窗口口径改为**累计 9 小时**（原 8 小时），单篇均耗按 **17.5 min**（间隔均值 13 + 执行 4.5）计，
  28 篇上限仍可在窗内跑完。来源：用户 2026-10-22 原话「压缩间隔8-18分钟。窗口将调整至累计9小时」。
  同步改动：`helpers/publish_interval.py`（常量 + docstring + argparse help）、`SKILL.md` 范围段与沿革说明、
  本文件、`refs/01-detail.md` 的 `--max-block` 口径。`DEFAULT_MAX_BLOCK` 保持 **2400**（仍 ≥ 1080），无需下调。
  调用方约定：**专题 key（A/B/C）可再收窄到下沿 480–660s**，由调用方按 key 决定，守卫本身不区分分组。
- v1.4.2 (2026-10-21) 明确 `state/.guard.lock` 是**常驻文件、不是残留锁**：锁由内核按句柄管理，
  关句柄/进程崩溃即自动释放，文件里的 `pid` 只作超时排查用；**不得据此手工删锁**（2026-09-26 曾误删一次）。
  同时澄清 `release` 带错 `--reserve-id` 打印「未找到对应占位」是正常结果。
- v1.4.1 (2026-10-20) 上界 1920 → **1320**（用户拍板，目的：23 篇/日 8 小时收口）；`--max-block` 要求 ≥ 1320。
- v1.4.0 (2026-10-09) 由 480–720 秒放宽到 660–1920 秒（用户拍板）。
- v1.3.0 及更早：`reserve` 单锁内完成查重 + 间隔判定 + pending 占位（修 TOCTOU 重复发布）；
  `record` 按 `note_id` 幂等；`--pending-ttl`（默认 1800s）自动回收占位。
