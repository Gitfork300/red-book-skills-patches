# publish-preflight-guard（发布前总检查与队列控制）

> 来源：2026-09-10 批量发布返工。
> 核心结论：**已发布的笔记改不回来**——脚本不能编辑，只能在 App 里人工改，且编辑要重新过审。
> 所以所有闸门必须前置到发布前；已经排上队但还没发出去的稿，都还能拦下来。

## 一、典型事故（为什么要有这个 patch）

5 篇批量发布，第 1 篇 23:56 发出后才发现三个问题：

1. 第 2/3/4 篇正文 1159 / 1134 / 1065 字，**全部超过 1000 字上限**
2. 封面是简单几何抽象的示意图，**用户明确不满意**
3. 活动类稿件**没写"需邀约 / 需登记 / 需审核"**，读者会白跑

后果：后 4 篇拦下重做（还好没发出去），第 1 篇只能人工编辑补救。

2026-09-11 又暴露第二类问题：**时效合格 ≠ 该发**。
前海智库院长论坛（9/12 深圳）时效上完全合规（次日开幕），
但它"不面向普通公众开放报名、也无线上直播"，读者既去不了也看不了，
仍在 00:58 发了出去。此后新增第 3 项「可发布资格」闸门。

## 二、发布前总检查（逐条打勾，任一不过不得排队）

| # | 检查项 | 判据 | 归属 |
|---|---|---|---|
| 1 | **选题查重** | 跑 `dup_check.py --title "<待发标题>"`，退出码 **0**。**按"事件"判，不按标题字面**——同一活动两稿措辞不同，精确匹配查不出来 | `publish-loop-guard` |
| 2 | **地域范围** | 会展活动类必跑 `geo_check.py --city/--text`，退出码 **0**——**只发江浙沪或珠三角**，其他地区一律排除（研究成果/政策类不受限） | `timeliness-window` |
| 3 | **时效窗口** | 活动类必跑 `check_window.py --start/--deadline`，退出码 **0 或 3**（须是"时效通过"，不能是 1）——近 7 天在举行，或报名截止在 7 天内 | `timeliness-window` |
| 4 | **可发布资格** | 活动类必传 `--live` 与 `--public-signup`：**无直播且普通观众无法报名 → 不发**；有直播 → 文案必须写明平台/时间/是否需预约 | `timeliness-window` |
| 5 | 事实与时效 | 时间/价格/人数双源核实；时效性内容查 7 日内信源 | `writing-facts-only` |
| 6 | 标题说明内容 | 不是"流水号+日期"式，含主体 + 看点或门槛 | `writing-facts-only` |
| 7 | 参与方式写全 | 邀约 / 登记 / 审核 / 截止时间 / 入场凭证 / 名额限制 | `writing-facts-only` |
| 8 | 用词预检 | `check_wording.py` 退出码为 **0**（含来源标注也要查）。**正文/标题一律不出现网址或裸域名**（`github.com/xxx`、`xxx.ai`、`www.xxx.com` 与 `https://` 同罪）；来源只写"机构名+项目名+论文编号" | `safe-wording-guard` |
| 9 | 字数硬限 | 标题 ≤20（按 18 留余量）、正文 ≤1000，且要**实测字数** | `safe-wording-guard` |
| 10 | 封面合规 | 真实感优先，无二维码 / 人物 / 文字 / 地图 / 完整人形机器人 | `cover-image-rules` |
| 11 | 封面文件核对 | 数量对得上、每张实际打开看过、没有被同名覆盖 | `cover-image-rules` |
| 12 | AI 声明 | 含 AI 图或 AI 文 → 传 `--content-declaration` | `cover-image-rules` |
| 13 | 间隔闸门 | **8~12 分钟随机**（下限 8 分钟），抽签写入 `next_gap`；或交给队列自动等待（`wait --max-block 900`） | `publish-interval-guard` |
| 14 | **选题配额** | 高频选题限量：**台风影响类每自然日至多 1 篇**（含预警/热带低压/扰动）；跑 `quota_check.py --kind typhoon`，退出码 0 才可发 | `timeliness-window` |
| 15 | **网络可达性** | 跑 `net_probe.py`，退出码 **0**。**必须真做 TLS 握手**——TCP 可连 / `ping` 通 / 80 端口返回 302 都不算数 | `windows-sandbox-workaround` |

> 第 2、3、4、14 条是"选题闸门"，且**按 2→3→4 的顺序判**：先划地域（外地的直接排除，不进入后续判断），
> 再判时效、资格、配额，最后才动笔。时效不合格的远期活动进待发池；
> 资格不合格（读者既去不了也看不了）的直接不发，不要写稿；配额已满的压到次日。
> 第 9 条最容易漏：加了内容之后字数会变，**每次改稿都要重跑字数检查**，不要凭印象。
> 第 15 条是**发布动作的闸门**：不可达时不要空转重试（会烧掉间隔配额），
> 先等网络恢复，再按漏发复核流程补发。见 `windows-sandbox-workaround` 的判定表。

## 三、批量队列的控制

### 0. 「启动」= 自动跑全流程 + 挂 30 分钟漏发复核

用户说「启动」时的编排要求见 patch：`publish-loop-guard`（priority 28）。摘要：

- 启动即**自动检索**展会/活动 → 时效 → 资格 → 配额 → 写稿 → 预检 → 发布
- 启动时把本次队列所有 key 写入 `publish-loop-guard/state/inflight.json`
- 同时起看门狗 `watch_missing.py --interval 1800`，**每 30 分钟**复核一次历史文章是否漏发
- 发现漏发**不直接重发**：必须重跑完整预检，内容不合规的先改稿，再按随机间隔补发；
  时效/资格已不合格的登记待发池
- 队列跑完（无论成败）必须**清空 `inflight.json`**，否则漏发复核永久失效
- **顺序不能反**：先写 `inflight.json`，再起看门狗；反了首轮会把整批在队稿件误报成漏发
- 用户要求「跑 N 小时后停」时，把截止时间写成队列脚本里的常量，判定点放在**间隔等待之后、提交之前**

### 1. 稿件在"发布那一刻"才被读取

批量脚本（如 `xhs_batch_publish_*.py`）一般在每篇的发布函数里才 `open()` 标题/正文/封面，
不是启动时一次读完。因此：

- **改磁盘上的稿件，对尚未发布的篇章有效**
- 改文件要趁那一篇**还在等待间隔**；已经读到内存的改不了

### 2. 发现问题可以安全停下队列

稿件尚未真正发布（仍在间隔等待）时，结束批量进程是安全的：

```powershell
# 按命令行匹配，避免误杀其他 python
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like "*xhs_batch_publish*" } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

# 清掉残留 Chrome
Get-Process chrome -ErrorAction SilentlyContinue | ForEach-Object { Stop-Process -Id $_.Id -Force }
```

停下后的流程：改稿件 → 改脚本（封面路径 / 待发列表）→ 重新排队。
**已发出去的那一篇单独人工处理，不要重发**（会变成重复内容）。

### 3. 跳过已发篇章

改批量脚本的 `NOTES` 列表，把已成功的条目删掉再跑，避免重复发布。

## 四、已发布笔记的补救

- 脚本**不能**编辑已发布笔记，只能走 App：「我」→ 笔记 → 右上角 → 编辑（标题/正文/封面都可改）
- 做法：把修订稿另存为 `*_title_rev.txt` / `*_content_rev.txt`，**先跑预检确认合规**，再整体复制替换
- 换封面时同样要满足 `cover-image-rules`（真实感、无二维码人物）
- 编辑后建议再跑一次 `verify-note` 确认状态正常
