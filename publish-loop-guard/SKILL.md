# publish-loop-guard

> Patch：**「启动」触发词 + 长流程漏发复核**。
> 1）用户说「启动」= 自动检索展会/活动并走完整发布流程；
> 2）流程运行期间，每 30 分钟复核一次历史文章是否漏发，漏发必须重新过预检再补发。

## 一、「启动」触发词

用户单独说 **「启动」**（或「启动发布」「按流程启动」）时，不再等补充指令，直接按下面顺序自动跑：

| 步 | 动作 | 依据 patch |
| --- | --- | --- |
| 1 | **检索**近期展会 / AI 活动 / 政策类选题（含用户既定领域） | — |
| 2 | **时效窗口**：只留近 7 天在举行 / 近 7 天需报名的 | `timeliness-window` |
| 3 | **可发布资格**：无直播且普通观众无法报名 → 直接不发 | `timeliness-window` |
| 4 | **选题配额**：台风影响类每日 ≤ 1 篇 | `timeliness-window` |
| 5 | **选题查重**（按事件、不按标题字面）：每条待发标题跑 `dup_check.py --title`，退出码 0 | 本 patch |
| 6 | 写稿 → **用词/字数预检** → 生成封面 → 发布前 15 项总检查 | `writing-facts-only` `safe-wording-guard` `cover-image-rules` `publish-preflight-guard` |
| 7 | **按 8~12 分钟随机间隔**逐篇发布（每篇 verify 通过才计间隔） | `publish-interval-guard` |
| 8 | 流程全程挂 **30 分钟漏发复核** | 本 patch |
| 9 | 逐篇回报 `note_id`，结束时报总表 | — |

**启动时必须做的两件事**（否则后面复核会误判）：

1. 把本次队列的所有 key 写入 `state/inflight.json`
2. 起一个后台看门狗：`helpers/watch_missing.py`

**启动时必须遵守的既有要求**（用户 2026-09-10/11 明确过，此处汇总，细节仍以对应 patch 为准）：

- 活动必须写明**参与方式**（邀约 / 登记 / 审核 / 截止 / 凭证 / 名额）；有直播必须写明平台、时间、是否需预约
- 标题**说清内容**，不用「流水号 + 日期」式命名；标题 ≤ 20 字
- 封面**真实感照片优先**（禁几何抽象、二维码、具体人物、完整人形机器人、地图/边界），必带 AI 水印/声明
- 只陈述事实，不做评论与建议；来源标注在正文末尾
- 涉及港澳台必须写「中国香港 / 中国澳门 / 中国台湾地区」

### 排队前的选题查重（按事件，不按标题字面）

`check_missing.py` 用**标题精确匹配**判断"发没发过"——对"漏发复核"是对的，
但拿它**查重会漏**：同一场活动两次写稿，标题措辞必然不同，精确匹配永远判成"没发过"。

2026-09-11 实录：`浦江创新论坛AI科研专题13日开幕`（00:48 已发）与
`浦江创新论坛设AI与类脑专题`（06:12 又发）是**同一场活动**（第十九届浦江创新论坛，9/11-14 上海），
精确匹配没拦住，读者侧表现为重复内容。

排队前对**每一条**待发标题跑：

```bash
python helpers/dup_check.py --title "<待发标题>"    # 退出码 0 才可排队
```

- 命中「**事件标识相同**」（以 论坛/大会/峰会/展/博览会/年会… 结尾的专名一致）→ 高置信重复：
  **同一活动默认只保留一篇**，多角度报道需人工确认后放行
- `--title` 模式同时启用「公共子串 ≥ 5 字」信号（措辞不同但事件名会照抄）
- 全量巡检：`python helpers/dup_check.py`（严格，误报极低）；`--loose` 会多看出一批同事件系列稿
- 日期串（`9月11日`）与数字串**不作为重复证据**，已在脚本内排除

## 二、30 分钟漏发复核

### 为什么要

批量发布是 1~2 小时的长流程。中途可能发生：

- 发布进程超时 / 被杀 → 静默跳过一篇
- 间隔守卫 `WAIT_INCOMPLETE` → 该篇直接放弃
- `verify-note` 未通过 → 不记录、不重试
- 两个队列并存抢通道 → 互相干扰

agent 一边等间隔一边数"我发了几篇"必然出错。**把判定交给脚本，每 30 分钟无脑跑一次。**

### 复核要做什么

| 步 | 动作 |
| --- | --- |
| 1 | **先把本次队列的 key 写进 `state/inflight.json`**，再起看门狗（顺序不能反，见「已知坑」） |
| 2 | 立即跑一次基线：`check_missing.py`，确认返回 `OK 无漏发` |
| 3 | 起看门狗：`watch_missing.py --interval 1800`（每 30 分钟一轮，发现漏发即退出告警） |
| 4 | 看到 `ALERT_MISSING` → **不是直接重发** |
| 5 | 重新过完整预检：时效窗口 → 可发布资格 → 选题配额 → 用词/字数 → 封面 |
| 6 | 稿件内容不符合现行要求 → **改稿**（标题、参与方式、来源、封面）后再发 |
| 7 | 时效或资格已不合格 → 不补发，登记 `pending_pool.json` |
| 8 | 合规的补发，仍走 8~12 分钟随机间隔，并记录 `note_id` |

### 复核范围（只看最近几日 + 只读第一页）

复核是为了发现"这一批有没有漏"，**不是给整个账号做全量体检**。范围必须收窄：

| 维度 | 口径 | 原因 |
| --- | --- | --- |
| 稿件侧 | **只扫最近 2~3 天**改动的稿件（`check_missing.py --days 2`，默认值） | 长流程只涉及当批，老稿件早已结清 |
| 平台侧 | **只读 note-manager 第一页（最新 10 条）**，不翻页、**也不逐个切「已发布/审核中/未通过」标签** | 笔记按时间倒序，新发的必然在第一页；翻页或切标签成倍拉长耗时、放大风控暴露面，对漏发判定零增益 |
| 状态侧 | 只看 `已发布 / 审核中 / 未通过`，不追阅读量趋势 | 复核只回答"在不在、通没通过" |

平台侧轻量速查（浏览器侧只读一眼）：

```bash
python helpers/recent_published.py --days 2      # 第一页 10 条里，最近 2 天的
python helpers/recent_published.py --status 未通过
```

退出码 `1` = 近期存在非「已发布」条目（审核中/未通过），需留意；`2` = 环境问题（Chrome/登录/依赖）。

> ⚠️ **不要为了"查全"去翻页**。历史上有一次为核对全账号翻到第 5 页，耗时数分钟且没有任何
> 额外结论——被删除、被驳回的稿件在**第一页或日志**上就已经能看出来。
> 真要审计历史，那是独立的一次性任务，不属于 30 分钟例行复核。

### 长批次的硬停止时间

当用户给出「跑 N 小时后就停」这类要求时，把**截止时间写进队列脚本**，而不是靠 agent 记时间：

```python
DEADLINE_TS = time.mktime(time.strptime("2026-09-11 07:50", "%Y-%m-%d %H:%M"))
# 主循环每篇之前 + 间隔等待之后再判一次；到点不再开新篇，剩余 key 标为「到点未发」
```

判定点要放在**间隔等待之后、真正提交之前**——否则等待 8~12 分钟期间到点，还是会多发一篇。


### 判定链（`check_missing.py`）

```
稿件标题文件  ──┐
               ├─→ 与 publish_log.json 精确匹配 ──命中──→ 已发
               │
               └─→ 排除：inflight（在队）/ abandoned（作废）/ pending_pool（待发池）
                        │
                        └─→ 剩余 = 疑似漏发
                                 └─ --verify → 平台确认确实没有 = 真漏发
```

关键：**「在队」不算漏发**。队列还在跑的篇目必须先写进 `inflight.json`，否则复核会把没轮到的正常稿件误报成漏发。

### 退出码

| 脚本 | 退出码 | 含义 |
| --- | --- | --- |
| `check_missing.py` | 0 | 无漏发 |
| | 1 | 有漏发 / 有未核验候选，需处置 |
| | 2 | 参数或环境错误 |
| `watch_missing.py` | 0 | 流程已结束且无漏发 |
| | 3 | **发现漏发，需介入** |
| | 4 | 达到 `--max-hours` 上限仍未结束 |

## 三、状态文件

| 文件 | 作用 | 谁维护 |
| --- | --- | --- |
| `state/inflight.json` | 当前队列在发/待发的 key 列表 | 流程启动时写入；**跑完必须清空** |
| `state/abandoned.json` | `keys` 明确作废永不补发；`files` 单个稿件文件不参与复核 | 出现口径变更 / 废弃修订稿时追加 |
| `timeliness-window/state/pending_pool.json` | 时效或资格不合格的待发池 | 复用，不重复造 |

## 四、使用

```bash
PY=<red-book-skills>/.venv/Scripts/python.exe
P=~/.workbuddy/skills/red-book-skills-patches/publish-loop-guard

# 一次性复核（默认只扫最近 2 天的稿件）
$PY $P/helpers/check_missing.py

# 队列场景：只查本批 keys（最准）
$PY $P/helpers/check_missing.py --keys ex0911_4,hk0911a_1,hk0911a_2

# 需要平台确认时（要 Chrome + 9222）
$PY $P/helpers/check_missing.py --verify

# 流程期间挂看门狗（每 30 分钟）
$PY $P/helpers/watch_missing.py --interval 1800 --max-hours 6

# 平台侧轻量速查（只读第一页，不翻页）
$PY $P/helpers/recent_published.py --days 2

# 台风配额
$PY <patches>/timeliness-window/helpers/quota_check.py --kind typhoon
```

> `recent_published.py` 会自动切到 skill 的 `.venv` 解释器（用系统 Python 跑也行）。

## 五、与其他 patch 的关系

- 依赖时序：`timeliness-window`（时效/资格/配额）→ `publish-preflight-guard`（总检查 + 队列）→ 本 patch（触发词 + 漏发复核）→ `publish-interval-guard`（间隔）
- 本 patch **不改任何脚本**，纯流程编排 + 两个只读复核 helper
- `check_missing.py` 只读稿件目录、发布日志、状态文件；唯一写操作是 `--verify` 时触发平台查询

## 六、已知坑

- **`inflight.json` 忘记清空** → 漏发永远查不出来。队列结束（无论成败）必须先清空再跑最后一次复核。
- **不作废的废弃稿留在稿件目录** → 每轮都误报。废弃稿要写进 `abandoned.json` 的 `keys` 或 `files`。
- **`--verify` 有成本**：每篇要几十秒，且要占用 9222。批量时先用默认模式筛，再对少量候选 `--verify`。
- **不要为"查全"翻页**：平台侧核验只读第一页；翻到第 2 页以后既慢又无结论（2026-09-11 实测）。
- **时间口径**：配额与复核都按**本地时间**的自然日 / mtime 计算。
