# publish-loop-guard / refs — 标准进度报告（「进度」触发词）

> 2026-10-16 用户拍板：「预计推进表写入 skill 作为一个标准流程进行。只要我问道 进度 进展 推进情况」。
> 触发即回执，不等补充指令（与「收尾/落盘」触发词同款模式）。

## 一、报告四块结构（固定，缺块即残缺）

| 块 | 内容 | 数据来源 |
|---|---|---|
| **① 分组进度表** | 每组「已建仓 / 已发布 / 待发」三列 + 明细（key+状态标记）；末行合计 | jobs 文件扫建仓；`_NNNN_pub_progress.json` 数 published |
| **② 预计推进表** | 按当前速率推算「时段 × 预计进度 × 对应组」的推进表；给出收官 ETA 与数学账 | progress/jobs 文件 + 当前间隔守卫 IMIN/IMAX；`publish_log.json` 的 `next_gap` 只判断下一篇何时可发，不作篇数或整批进度来源 |
| **③ 小任务进度** | 天气自动化 / 评论巡检 / 提醒登记 / Canary 计划 / 重发项 / bug 债 / 日终收口 | memory 当日日志 + automation 列表 + 各 state 文件 |
| **④ 阻塞与风险** | 当前卡点（事故、pending、Chrome、平台侧）、需用户拍板项（≤3 条，标注 ⚠️） | 实时诊断：pending 残留、9333 LISTENING、creator 可达性 |

### ① 分组进度表（**列结构固定，照抄**）

用户 2026-10-16 拍板：**必须逐组列明细**（不是只给数字），因为要看「哪几篇发了、哪几篇待发」。

```
| 组 | 内容 | 已建仓 | 已发布 | 待发 | 明细 |
|---|---|---|---|---|---|
| **A** | 专题一 · CICAI（江浙沪） | 5 | **5** ✅ | 0 | a1016_01~05 全发（07:54–10:21） |
| **B** | 专题二 · IAB HK C26（珠三角港澳） | 5 | **5** ✅ | 0 | b1016_01~05 全发（10:34–12:05） |
| **E** | 展会 · 江浙沪 | 5 | **3** | 2 | e1016_01~03 ✅；e1016_04~05 待发 |
| **合计** | | **42** | **16** | **26** | 覆盖 N 组完整收官 |
```

- 组名**加粗**；内容列注明子类（专题一/二、展会地域、技术方向）；
- 已发布数**加粗**，满仓（已发=建仓）该格加 `✅`；
- 「明细」列两种写法：① 已全发 → `a1016_01~05 全发（HH:MM–HH:MM）`；
  ② 部分发 → `e1016_01~03 ✅；e1016_04~05 待发`（key 段连续用 `~` 合并）；
  需强调单篇时用 `a1016_04 15:45:22 ✅`（key + 时间 + 勾）；
- 若某组是当日**补发**混入，内容列注明（如「活动综合（含补发 i1015_05）」）；
- **末行合计**必备：`**合计** | | **建仓** | **已发** | **待发** | 覆盖 N 组完整收官`；
- **本段战果行**（可选但推荐）：表下补一句「本段战果（HH:MM→HH:MM，约 N 分钟）：新增 N 篇（key 时间…），X 组收官」。

### ② 预计推进表（**分段到组，照抄**）

```
按间隔 <IMIN>–<IMAX>s（周期约 <间隔中值+80>s/篇）：剩余 N 篇 ≈ X 小时，预计 HH:MM 前后收官（22:00 日界内）。

| 时段 | 预计进度 | 对应组 |
|---|---|---|
| HH:MM–HH:MM | 17–21 篇 | **F 组 5 篇**（珠三角港澳展会） |
| HH:MM–HH:MM | 22–26 篇 | **G 组 5 篇**（AI 算力具身） |
| … | … | … |
| HH:MM–HH:MM | 38–42 篇 | **Y 组 5 篇**（Canary 顺延稿）收官 |
```

- 先给**一句话数学账**（间隔口径 + 剩余篇数 + ETA + 是否在日界内）；
- 表内**每行对应一个组或一次收官**，进度列写「起始篇号–结束篇号 篇」；
- 分组名**加粗**并在括号里注明内容；
- 若间隔为压缩特例，数学账里**必须注明授权依据与恢复日期**。

### ③ 小任务清单（逐项给状态 ✅/⚠️/🔴/⏳，无动作也要写「无」）

固定 8 项，按此顺序：

| 项 | 判据 |
|---|---|
| 天气自动化 | recurring 是否存在、下次触发时间 |
| 评论/私信巡检 | 当日是否跑、recurring 是否存活（**丢失=⚠️**） |
| 评论到期提醒 | `COMMENT_REMINDERS.md` 是否有过期未执行项（过期=🔴） |
| Canary 计划 | `_CANARY_PLAN_*.md` 假设与判定线是否写、判定时点 |
| 待重发项 | 是否在今日队列、活动日期是否在时效窗 |
| bug 债 | 新增（B-0xx）/ 未闭环条数 |
| 日终收口 | 是否到窗口（21:30 停链 / 22:00 日界） |

（例：`| 评论/私信巡检 | ⚠️ **recurring 丢失**，待拍板是否重建 |`）

## 二、硬性要求（六条）

1. **数字必须现查现算**：进度以 `_NNNN_pub_progress.json` 的 published 计数为准
   （**禁用 publish_log.json 推算篇数**——它含 pending/`__chain__` circuit_break 等非篇记录，B-048 同族教训）；
   建仓数以 jobs 文件行数为准。
2. **预计推进表必须带数学账**：剩余篇数 ×（随机间隔中值 + 单篇发布耗时 80s）→ ETA；
   间隔下限/上限两种边界都要算（下限 = 最早可能，上限 = 最晚可能）。ETA 超 22:00 日界
   或超用户给定收官点时，**先算账再用 AskUserQuestion 请示**（压缩间隔属规则级变更，
   需用户授权；660–1920s 为默认拍板口径，10-09 定）。
3. **小任务块不省略**：评论/私信巡检、天气自动化、到期提醒、Canary、待重发项、
   日终收口——逐项给状态，没有动作的也要写「无」。
4. **拍板项 ≤3 条**，与发布链自动推进解耦：报告不得因等待拍板而延迟发布链。
5. **报告本身不替代处置**：发现事故（卡死/pending/环境失败）先处置后报告，
   报告中注明「已修复 + 登记 B-0xx」。
6. **列结构与符号照抄模板**：① 表六列（组/内容/已建仓/已发布/待发/明细）不得增删；
   组名与「已发布」数加粗；满仓加 ✅；末行合计必备；标记只用 ✅/⚠️/🔴/⏳ 四种
   （✅ 完成、⚠️ 需关注、🔴 阻塞/过期、⏳ 待办）——**不用其他 emoji**。

### ④ 阻塞与风险（样板）

```
- ✅ **无阻塞**：pending 残留 0、Chrome 9333 正常 LISTENING（pid NNNN）、链运行中
- ⚠️ Chrome 今日已崩 N 次（HH:MM、HH:MM），现稳定；若再崩按手动命令行重建
- ⚠️ 收官 ETA HH:MM，收口动作安排在 21:30 停链后做
```

- 首行用 ✅ 明示「有无阻塞」（无阻塞也要写，不要留空）；
- 每条一个符号 + 一句话，**拍板项 ≤3 条**放最后，逐条编号；
- 事故类必须先在同条里写「已处置」与 B 编号。

## 三、环境类失败识别（④ 块的实时诊断口径）

| 症状 | 判据 | 处置 |
|---|---|---|
| Chrome 崩溃/闪退 | 9333 无 LISTENING 且 chrome 进程 0；launcher 起完即退 | 手动带参起 Chrome（launcher 方式会被沙箱回收，闪退）；查 profile Singleton 锁 |
| 登录态失效 | check-login NOT LOGGED IN / URL 落 /login | **需用户扫码**（人工介入不可绕过）；同时全链 rc=5 快速失败不空转 |
| 平台侧不可达 | curl creator HTTP 非 200（B-049 家族） | 等平台恢复；间隔拉到 300s/档 |
| 稿件级失败 | 输出无环境特征、rc=3/4 | 同篇 ≥2 次移队尾，换下一篇 |

环境类失败特征串（`_publish_one_1016.py` rc=5 判据）：`chrome-error://chromewebdata`、
`NOT LOGGED IN`、`/login`、`Could not find a safe, visible`、`"ok": false, "waited_s"`。
